# How we write API specs

Every API is written down and approved before it is built. One markdown file per spec, grouped by module.

## Files and numbers

| Module | Folder | Numbers |
|---|---|---|
| Content | `specs/content/` | API-001 – API-009 |
| Rendering | `specs/rendering/` | API-010 – API-019 |
| Publishing | `specs/publishing/` | API-020 – API-029 |

File name: `API-NNN-<slug>.md`. Start from [TEMPLATE.md](TEMPLATE.md).

## Header

| Key | Meaning |
|---|---|
| `id` | `API-NNN`, unique |
| `title` | Short name |
| `domain` | Module folder name |
| `status` | `draft` · `in review` · `approved` · `built` |
| `owner` | Usually `api-architect` |
| `stories` | Issue numbers, e.g. `[7, 8]` |
| `depends_on` | Other spec ids, e.g. `[API-002]` |
| `version` | Raised on every change after approval |

Only a human sets `approved`. A spec moves to `built` in the PR that finishes its last story.

## House rules for the API

- JSON, `snake_case` fields, resource paths in plural (`/sites`, `/pages`).
- Ids are prefixed strings: `st_…` for sites, `pg_…` for pages, `rl_…` for releases.
- Errors: `{ "error": { "code": "page_not_found", "message": "…" } }`, with `code` in `snake_case`.
- Lists: `?limit=` (default 20, max 100) and `?cursor=`; responses have `items` and `next_cursor`.
- Writes that create something accept an `Idempotency-Key` header.
- Every limit is a number in the spec.

## Index

`specs/README.md` is generated by `node scripts/spec-index.mjs`. CI fails when a header is invalid, a dependency is unknown, an approved spec has open questions, or the index is stale.

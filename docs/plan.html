02 · Motion

The golden thread

One idea in three beats: the light draws the hexagon, the logo settles into the corner, the site appears around it. The brand builds the site.

Intro · 2.7 s
  • 0–0.85 s light traces the hexagon (sine ease)
  • 0.7–1.1 s gold fill and H
  • 1.25–2 s logo glides to the nav, site fades in
  • 1.7–2.7 s blocks settle, 70 ms apart
Loader · loop
  • Same hexagon and light, drawn and released in a 2 s loop.
  • Use while a site renders or publishes.
  • Small version (24 px) works as a button spinner.
  • Respect reduced motion: show the static logo instead.

Rules for all motion: one shape at a time, no flashes, slow in and slow out, nothing faster than 300 ms, and every motion ends where the next one starts.

03 · Product

A small builder, finished well

Owners compose pages from a fixed set of blocks, pick a theme and publish a static site with versions they can roll back. Editing happens through the API and a simple form-based admin; a visual editor comes later.

Content

Sites, pages, blocks

  • Sites with a slug and settings
  • Pages with title, slug and menu order
  • Blocks as an ordered list per page
  • 8 block types, each with a JSON schema
Rendering

Themes and HTML

  • 3 themes from design tokens
  • Page rendered to clean, accessible HTML
  • Draft preview per page
  • Same input, same output (snapshot tested)
Publishing

Releases

  • Publish a site as an immutable release
  • History of releases
  • One-click rollback
  • Serve the live release

Block types

Hero · Text · Image · Gallery · Cards · Blog list · Contact form · Embed. Each has a schema (fields, types, limits) that the API validates strictly and the renderer trusts.

Not in the MVP

Drag-and-drop editor, custom domains, multiple users per site, plugins, e-commerce, analytics. Each is a later phase once the core works.

04 · Architecture

A modular monolith

One deployable, three modules with hard boundaries. Each module is owned by one agent team, which makes the boundaries a real test of whether agents stay in their lane.

Choices

  • .NET 10 (LTS), ASP.NET Core minimal APIs
  • PostgreSQL with EF Core, one schema per module; SQLite allowed for local tests
  • Modules talk only through a .Contracts project: interfaces and events, never each other's internals
  • In-process events for "page changed" and "release published"
  • Rendering is pure: content + theme → HTML, no database access
  • Published releases stored as files (local folder now, blob storage later)

Quality gates

  • Architecture tests fail the build if a module references another's internals
  • Integration tests over HTTP with a real database in a container
  • Snapshot tests for rendered HTML per block type and theme
  • Spec index check: specs valid, approved specs only
  • dotnet format and analyzers on warnings-as-errors

05 · Agent factory

A studio of agents

The factory is a reusable Claude Code plugin with generic roles. Hivesite adds its own domain experts. Humans approve cases, specs and merges.

The flow of one story

R&D case→you approve→manager writes story→api-architect drafts spec→you approve spec PR→pm: tasks→domain dev builds PR→reviewer→tester→you merge

Role

How to work: in the agent file (instructions, tools, model). Generic, reused across projects.

Domain

What's true: in a skill per module (block schemas, rendering rules, release rules), preloaded by its developer.

Project

House rules: in CLAUDE.md at the root and per module, loaded when an agent works there.

Guardrails from day one: tools limited per role, each developer in its own worktree, a budget per story, three review rounds at most before a human steps in, and no agent ever merges.

06 · Specs & design

Written down before it's built

API designs are markdown pages with a header block, grouped by folder and indexed automatically. Visual design is tokens and block layouts, also in the repo.

## Purpose
Owners set the ordered blocks of a page.

## Endpoints
### PUT /pages/{id}/blocks
Auth: site owner

Request
{ "blocks": [ { "type": "hero",
  "data": { "title": "Hello",
            "subtitle": "Welcome" } } ] }

Response 200 { "page_id": "pg_31", "blocks": [...] }

Errors
- 400 invalid_block: data fails its schema
- 404 page_not_found
- 422 too_many_blocks: more than 40

## Open questions
- none

How specs stay organised

  • One folder per module: specs/content, rendering, publishing
  • specs/README.md is generated: by module, by status, open questions
  • CI fails on bad headers, unknown dependencies, or approved specs with open questions
  • Spec PRs and build PRs are always separate

Design in the repo

  • design/tokens.json: colors, type, spacing per theme
  • design/blocks/*.md: layout, states and limits per block type
  • design/brand/: logo, lockups and the motion samples from this page
  • Renderers only use tokens, never hard-coded values
